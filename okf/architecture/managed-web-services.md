# Summary

- Authority: Redeven owns each installed service's immutable snapshot, lifecycle, runtime identity, private data, and protected forward; the application owns its settings and credentials.
- Outcome: a [Service template](managed-web-service-templates.md) becomes one managed card with open, lifecycle, logs, retry, update when eligible, and uninstall actions.
- Invariants: one instance exists per family, Web ports bind only to loopback, lifecycle work is idempotent and serialized, destructive work verifies exact identity, and credentials never enter records or logs.
- Failure boundary: invalid identity, prerequisites, health, or artifacts fail closed without touching unrelated resources.

# Contract

## Deployment execution

Deployment streams environment check, artifact preparation, verification, install, start, health, and forward registration through the authenticated Local API. The template drawer owns submission only; after persistence, Renderer closes it and attaches the operation stream to the new service row. Only the row Cancel action cancels work, and deployment never force-opens a browser. Container and Image destinations come from Runtime. Image navigation accepts only a complete authoritative ID, reference, digest, tag, or pinned-reference alias; partial or missing matches do not move the list.

Host template queries expose one Runtime-derived, non-persistent schema-v1 lifecycle plan. It describes the actual npm or host-script driver, exact package identity, ordered Runtime work, and safe command templates without becoming a second execution or editor state. The generic npm driver installs only an exact package version into an isolated release directory, and the required start script remains the single launch entry through `REDEVEN_INSTALL_EXECUTABLE`. DeepSeek Web arguments include `--no-open`. User-authored scripts remain authoritative snapshot content; the plan labels their execution position with safe placeholders rather than echoing credentials, URL queries, or private absolute paths.

One Runtime operation record and event stream own each lifecycle action. The service-row disclosure is the only details entry and shows ordered stages, exact artifact, Compose image position, bytes, smoothed three-second rate, layers, and elapsed time. Known byte totals drive determinate progress; layer-only or npm work with no trustworthy total stays indeterminate. Exact local image cache hits report real RootFS layers and zero transferred bytes, never uncompressed image size. Elapsed time continues without CLI output. Ordinary changes persist and publish at most every 500 milliseconds; stage and terminal changes publish immediately, always after persistence. There is no duplicate dialog, polling, global progress, or second state source. Activity shimmer and Thinking Orbs become static under reduced motion.

An errored service exposes one structured `last_failure` projection. Its focusable status shows only the action, redacted user-facing explanation, stage, and time; an adjacent action copies a bounded diagnostic containing only persisted identifiers and sanitized fields. Secrets, raw commands, engine output, stacks, and workspace content never enter that diagnostic. The recovery button follows the persisted failed action: failed install retries install, failed start or restart performs Start against the existing Runtime, and failed stop retries Stop. It never converts an exact Start failure into reinstall or container replacement. Starting new work lets active progress replace the old error, successful completion clears the current error, and another failure replaces it. Historical operation context that was never persisted is omitted rather than inferred from template or service state.

Before execution, the instance saves the exact template revision and JSON bytes, SHA-256, family, workspace, versioned overrides, configuration revision and hash, release identity, and Runtime manifest. Reads hash stored bytes before strict typed decoding; reserialization is never an alternate identity. One effective-spec resolver serves install, retry, update, reconfigure, recovery, and verification. Later edits do not alter the installed snapshot, and an invalid override conflict fails before mutation. The default is a template-specific directory under the Environment home; a user replacement must remain an existing writable directory inside Environment filesystem scope.

## Instance configuration and reconfigure

The effective specification, settings API, typed Runtime fields, managed anchors, Admin risk plan, private secrets, stopped-state rebuild, rollback, and interaction contract are owned by [Managed Service instance configuration](managed-service-instance-configuration.md). Every lifecycle path consumes that one result; no Renderer-preserved or deployment-specific configuration path exists.

Host scripts run through `/bin/sh -eu` as the current OS user with workspace, private data, loopback host, reserved port, optional verified executable, and validated template environment. Start remains foreground. One Host process controller owns start, stop, uninstall, Runtime shutdown, and restart adoption. New identities bind service ID, process group, system boot identity, PID, and process start time. Restart adopts only a process whose complete fingerprint matches; a historical DeepSeek process additionally requires the exact managed executable tree, foreground Web command, loopback host, and saved port. Stop-script failure cannot bypass exact process-group cleanup, and PID-only ownership is never sufficient.

Single-container deployment pulls first and requires a verifiable immutable OCI digest. All managed container paths use one image-pull boundary. Pulls have a dedicated 30-minute maximum and terminate immediately on operation cancellation; the ordinary 10-second container-command limit does not apply. Timeout, registry reachability, manifest absence, access or rate limits, and exhausted storage remain distinct stable product errors. Raw engine output never crosses that error boundary, and diagnostics remain redacted. The default restricted profile creates the exact image with `cap-drop ALL`, `no-new-privileges`, a read-only root, PID limit, bridge networking, project-owned volumes, hardened tmpfs, and exactly one `127.0.0.1` host publication. The only exception is the Runtime-owned `interactive_desktop` profile described below; custom templates cannot request it.

Compose pins every image and hashes its private generated configuration. Only the entry service receives the loopback Web port. Each lifecycle action verifies configuration, project, one-container-per-service membership, labels, images, hardening, and sidecar isolation.

## Built-in DeepSeek Harness

Host template `deepseek-harness-host` and container template `deepseek-harness-container` own separate service families, so one Environment may install one instance of each while the Registry still rejects a duplicate of either exact family. The shared `deepseek-harness` identifier names only common product artifacts and private host runtime data; it is not a template or instance identity. Both definitions expose direct upstream candidates, but Redeven never installs a discovered release without explicit user selection and risk acknowledgement.

Host deployment supports Linux and macOS on amd64 and arm64. Revision 4 declares `@deepseek-ai/dsh` as a generic npm Host package, uses the Redeven-managed Node.js `24.19.0` runtime, and sets `DSH_HOME`, `HOME`, and `DSH_DESKTOP_ENABLED` through TemplateSpec v3 environment declarations. Installation uses the selected exact version and Registry integrity without a package lock, suppresses scripts during dependency placement, removes the temporary token configuration, then deliberately runs lifecycle scripts after confirmation. It verifies the direct package version, executable, integrity, Node artifact, and complete managed Runtime tree before committing the isolated release. The launcher binds the assigned loopback endpoint and suppresses upstream browser opening. A migrated Bundle instance continues to use its exact historical installation, log, and real data directories until a successful release update naturally replaces its runtime layout.

Container deployment identifies `ghcr.io/runzhliu/deepseek-harness` as community packaging, not a DeepSeek official distribution. Candidate selection resolves an exact current-platform OCI digest from GHCR; install and update pull that digest rather than a mutable tag. The template marks `market` tags as visible but non-deployable. The container runs non-root under the hardened policy, mounts a private data volume and selected workspace, publishes only Harness port `3080` to loopback, and never publishes `6080`/noVNC.

Both DeepSeek templates declare `desktop_loopback` as their default access mode. This does not widen container privileges or change Harness configuration: it gives the isolated Desktop target view a real `127.0.0.1` Origin while the Desktop gateway still traverses the protected Runtime forward. Models and other upstream local-browser checks therefore see a local browser without modifying Harness. Web Env App and system-browser opening are unavailable for this mode; users may explicitly switch the persisted forward to `unified_proxy` when broad client access matters more than local-browser compatibility.

Changing either built-in deployment requires reviewed source defaults, licenses, architecture, immutable identities, persistence, WebSocket, loopback, and protected-routing smoke tests. Discovery failure never disables an installed service or its lifecycle actions. Third-party notices distinguish reviewed defaults, directly selected on-demand software, and code embedded in Redeven. Candidate identity and update behavior are owned by [Managed Service release discovery and updates](managed-service-release-discovery.md).

## Built-in interactive desktops and updates

The two independent Webtop templates, their reserved `interactive_desktop` profile, risk acknowledgement, immutable platform artifacts, and journaled update/rollback flow are owned by [LinuxServer Webtop](linuxserver-webtop.md). They still use this contract's single generic container lifecycle, protected forward, operation stream, persistence, and exact-identity checks; no second driver or Renderer state machine exists.

## Persistence and recovery

Port-forward Registry schema v9 is the contiguous successor of v1 through v8. The v7-to-v8 edge upgrades every stored TemplateSpec v1 document to v2, materializes the generic npm declaration for historical DeepSeek Host snapshots, converts the retired DeepSeek `native` and `docker` deployment names, and adds a non-null schema-v1 release identity plus SHA-256 to every service. Exact historical OCI artifacts and the reviewed DeepSeek npm integrity are migrated; an ambiguous package or non-digest container identity fails before commit. The v8-to-v9 edge introduces TemplateSpec v3 but changes only strictly identified built-in DeepSeek Host snapshots by adding their managed environment. Other built-in and custom v2 documents remain byte-for-byte valid and are upgraded to v3 only by an explicit later template edit or duplication. The edge recomputes only affected exact JSON digests and restores desired `running` only when the latest failure is the Runtime-generated recovery Start and no later user operation exists. Workspaces, historical runtime and data paths, volumes, configuration, secrets, forwards, resources, release identity, operation history, failure records, timestamps, user scripts, and journals remain unchanged.

The Registry opens and completes every required migration before the Managed Service Manager or API accepts requests. Every edge verifies its reviewed source and target, and the migration, digest updates, version metadata, document validation, and final structure commit in one transaction. Failure rolls back to the last supported database; Redeven never deletes, replaces, silently repairs, or asks the user to recreate it. Wrong kind, structural drift, invalid progress or release documents, ambiguous history, mismatched exact DeepSeek families, and future versions fail closed with an actionable diagnostic. Reopening current v9 is idempotent. Any later persistent-format change must append its contiguous migration and preserve this lineage rather than raising the minimum version or relying on decoder fallback.

`managed_web_service_resources` is the sole durable authority for managed container-volume identity. A strictly identified built-in `deepseek-harness-container` that predates that table may import its retired `deepseek-harness/docker-volume.json` marker once through the generic Container resource loader. Import requires the exact deterministic volume name, a valid saved creation time, and a matching live Docker volume inspection; it commits resource ID `data` before best-effort marker deletion. Missing, malformed, unavailable, or mismatched identity fails closed without starting, creating, replacing, moving, renaming, mounting, or deleting a container or volume. A cleanup interruption is safe and idempotent because the committed Registry resource wins on every later load. When the latest operation is exactly a failed Start with `DATA_IDENTITY_MISSING`, service state still carries that same error, and no later user operation exists, a successful import restores desired `running` and schedules the ordinary Start path once; all other failures and explicit later actions remain untouched. The retired DeepSeek Docker lifecycle driver is not callable by current operations; `native` and `docker` deployment literals exist only in historical Registry migration input.

Service, protected forward, and initial install operation are created in one transaction. Terminal operation and current service error also commit together. New forward identities are DNS-safe across Runtime proxy, sandbox host, and Desktop route; historical underscore identities receive only a temporary browser alias. Matching request retries return the original operation, conflicting reuse fails, and at most one operation is active per service.

Startup marks incomplete work `interrupted`, cleans only verifiable partial resources, and waits for Retry, except that an interrupted reviewed update follows its persisted finalize-or-rollback journal. A terminal instance with desired state `running` receives a recovery Start. A v8 automatic recovery failure repaired by v9 retains its failure operation for history, retries once through this same rule, and clears only the current error after success. Shutdown stops exact known runtimes while retaining desired state. Stop preserves the forward and card.

Uninstall retains data by default. Deleting data requires a second destructive confirmation and administrator or owner authority. Each deployment driver owns one stop-and-remove sequence; the lifecycle manager does not issue a second stop. Container and Compose removal verifies the persisted Runtime ID, deterministic managed name or project, service label, image identity, configuration, and managed volume identity without requiring an otherwise executable configuration snapshot. A strictly identified historical DeepSeek container may retain its deterministic `redeven-dsh-*` name; new and replacement containers use only `redeven-mws-*`. Name compatibility never relaxes ID, label, pinned image, digest, or configuration checks. A container confirmed absent is already removed; engine unavailability or any ownership mismatch still fails closed with a field-specific code. Host uninstall scripts remain executable authority and therefore require a valid verified snapshot. Successful removal atomically deletes the service and forward while retaining terminal operation history.

Health succeeds only after the application responds on its assigned loopback port. Redeven exposes the stable identity through the Local and remote protected routes defined by [Web Service browser sessions](web-service-browser-sessions.md).

## Local API and authorization

Catalog, list, and create live under `/_redeven_proxy/api/managed-web-services`; lifecycle and logs use `{id}` routes, and cancellation/events use operation routes. Candidate POST routes exist under both template and service IDs. Install requires an exact `template_id`, access mode, and optional opaque `target_release_id`; the Manager revalidates source, scope, platform, and risks before work. `progress_detail` and `last_failure` are Runtime-owned projections, not Renderer reconstructions. Reads require Web Service read permission; mutations require read, write, and execute, with Admin or owner for high-risk reconfigure and data deletion. Bodies and audits exclude scripts, values, candidate URLs, notices, and secrets.

# Boundaries

This contract does not include Windows host deployment, cross-Environment scheduling, nested Docker, automatic upgrades, migration between deployment kinds, public exposure of the managed primary Web endpoint, Webtop variants beyond the two reviewed templates, automatic GPU or DinD enablement, host Docker management, or Redeven management of application API keys. Explicit custom-template ports and high-risk runtime access are user-owned exceptions admitted only through the typed Admin-confirmed Resource Plan.
