# Summary

Terminal activity is a renderer-first view over canonical Floret v4 Activity items, not a second process lifecycle. Redeven maps display data only from typed `ActivityItem.presentation`, so the compact row shows `Shell` and the authored command instead of a protocol name. Approval state remains available to the actionable composer but never becomes ordinary activity presentation. Stable activity identity preserves user disclosure and viewport state across current-view replacements. Terminal output may refresh Redeven process handles, but canonical status and completion remain Floret-owned. Measured disclosure, local scrolling, transcript following, and reduced-motion handling preserve reading intent.

# Contract

## Mechanism

Terminal process activity remains part of the canonical current view. The Floret v4 contract keeps `label`, `description`, `renderer`, `chips`, `target_refs`, and `payload` under `ActivityItem.presentation`; identity and lifecycle remain on the item itself. Redeven accepts only the typed nested presentation and maps it consistently from bootstrap and live current replacement. A terminal row receives its command, status, process id, retained snapshot, and sequence facts from that presentation. Its compact trigger always renders `Shell` plus the real command. `terminal.exec` publishes the process id when the PTY starts, so `yield_ms` affects only provider waiting, not when the user can inspect progress. The public payload excludes host-local `cwd`, `workdir`, and `stdin`.

Expanded terminal rows are read-only product presentation. Completed status, output, exit code, and duration come from the canonical Floret Activity payload. Historical completed payloads that contain canonical output but predate sequence metadata render as an unsequenced static snapshot; live deltas remain sequence-strict. While an Activity is running, a newer exec snapshot replaces the cumulative view and a contiguous process-read delta appends to it. Equal or older snapshots are ignored, an empty delta does not clear output, and an explicit truncated gap replaces the unavailable prefix. Flower requests only `after_seq` for a running Activity with a public process id. A terminal process-read response may stop local polling but cannot change canonical Activity status or create lifecycle facts. Raw AppServer errors map to localized live-output or terminal-action failures. The surface offers icon actions to reveal and copy the command and caps output at five visual lines. Terminal execution and settlement belong to [Terminal tool runtime](../ai/terminal-tool-runtime.md) and [Floret thread runtime integration](../ai/floret-thread-runtime.md), not this UI concept.

# Boundaries

Flower activity details are renderer-first product views, not generic payload inspectors. `error`, `terminal`, `file`, `patch`, `web_search`, `question`, `completion`, `todos`, and `subagents` each have an explicit display model that prioritizes the information a normal user is trying to inspect: failure reason, terminal output, file content, diffs, search results, prompts and choices, outcomes, todo lists, or delegated task status. Read, list, find, grep, glob, and web operations expose only semantic scalar values or bounded scalar lists such as path, root, query, pattern, URL, and count. Unknown tools use a neutral `Called <semantic label>` title and the same safe scalar allowlist; a human label does not authorize rendering nested `data`, `result`, or arbitrary protocol JSON. Failed tools render the public error summary in the compact row and keep the complete public message in a collapsed error detail without exposing error codes, retryability flags, item ids, tool ids, or lifecycle diagnostics. Successful tools do not show generic completion summaries or event-code details such as `tool execution completed`, `todos.updated`, `file.updated`, `success`, `completed`, or `ok`. Rich structured metadata remains available only for explicitly designed product renderers such as OKF and skill activation.

Flower activity disclosure is presentation state over the canonical activity lifecycle, not a second execution state machine. Every stateful activity view uses one semantic identity composed from thread, run, turn, and canonical `item_id`; status, payload, message block position, item position, and renderer object identity are not part of that identity. A canonical current-view replacement may move an activity between message blocks, but it must reuse the same activity row, disclosure controller, detail component, and terminal viewport. A live projection may first expose the stable item without a renderer or detail payload and later enrich that same item; the row keeps its DOM identity, while the disclosure trigger remains bound and its native disabled state follows detail availability. All pending, running, waiting, completed, and failed activity details remain closed until the user explicitly opens them. A manual expand or collapse persists across later lifecycle and canonical replacement updates for that stable item. Running terminal detail remains available on demand, but background progress never mounts detail or changes transcript geometry merely because time passed. Opening uses a 360 ms measured-height animation and closing uses a 300 ms animation. Approval state is not a row badge, chip, metadata line, title suffix, tooltip, expanded detail, or ordinary activity ARIA label. When an approval is actionable, the composer exclusively owns its approve and reject controls; completing a decision removes that dock without adding `approved` or any other approval outcome to history.

Open activity detail owns its real pixel height. A shared disclosure motion controller mounts at `0px`, measures the nearest detail content from its bounding rectangle, and uses the Chromium `ResizeObserver` and Web Animations APIs as required platform capabilities. Opening, resizing, retargeting, reversal, and closing are all owned by one current animation; its `finished` promise is the only completion signal that may advance presence state or unmount content. CSS does not own a second height-transition clock, and animation completion is not inferred from elapsed timers. Consecutive content changes cancel the previous animation and redirect the current visual height to the latest measured target. Content growth and shrinkage use a 280 ms animation, including terminal polling, command expansion, responsive reflow, error replacement, and disappearing controls. The nearest detail disclosure owns this dynamic resize; the Env App timeline wrapper animates only its own open or close, preventing nested height animations from compounding movement. Detail content remains capped at `min(42rem, 72vh)`, and terminal output remains capped at five visual lines; growth beyond those limits becomes local scrolling instead of continuing to move the conversation.

Flower schedules its existing transcript-tail follower on every disclosure animation frame. It preserves the bottom anchor only while the user is already following latest content, and it never forces a conversation back to the end after the user scrolls upward. Env App continues to use `VirtualMessageList` row `ResizeObserver` handling: following mode applies each intermediate height delta, while paused mode restores the captured viewport anchor after every observed height. Terminal panels use a separate local 24 px near-bottom threshold. Binding or reopening a terminal viewport begins a new local viewing session at the latest line. Each output update receives one presentation frame: following mode scrolls to the bottom before reporting the output as presented, while paused mode preserves `scrollTop` and still reports presentation completion. Upward wheel or scroll pauses local following, returning to the bottom resumes it, and canonical activity replacement does not reset that choice. Reduced-motion presentation commits measured pixel height without animation and unmounts closed detail immediately. Running and waiting rows use only transform, opacity, or color animation; no infinite animation may change `left`, width, height, or another geometric layout property. Closed detail is not mounted, and mounted detail uses `content-visibility` containment. These presentation rules do not alter Floret activity status, event ordering, persistence, read state, audit state, or terminal settlement.
