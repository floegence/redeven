# Summary

After access first becomes ready, Env App owns one stable `EnvAIPage` and `FlowerSurface`. The published `BottomBarCompanion` provides a centered collapsed field and a bounded detail surface that grows upward without changing body geometry. The dedicated Activity Bar page and an available, unfiltered Workbench Flower widget are placements of that same product tree. Workbench selection controls canvas input and focus only; clearing selection never revokes Flower placement or engagement. Placement changes hosts, presentation, visibility, and engagement; it never creates a second Flower surface or changes Floret authority. Floret owns thread lifecycle state, while Redeven owns product placement, read acknowledgement, and ephemeral UI state.

# Contract

## Companion ownership

`@floegence/floe-webapp-core/layout` owns the reusable companion shell, fixed geometry, visual-viewport and safe-area clamping, motion phases, capture-phase outside dismissal, Escape routing, and explicit mount handling. Redeven consumes the published package and does not reuse `FloatingWindow` or `SurfaceFloatingLayer` for this surface. The companion has independent `retained`, `visible`, and `open` inputs: residency, product availability, and expanded geometry are not aliases for one another.

The desktop Bottom Bar is 28 CSS pixels high and keeps a symmetric three-track layout. Its 22-pixel anchor stays centered independently of environment and status controls and has a preferred maximum width of 360 pixels. Redeven requests a 544-pixel expanded width through the published `expandedWidth` contract; Floe centers and clamps that width to the safe visual viewport. Mobile keeps its 44-pixel fixed anchor rail above the measured mobile tab bar. Each anchor is a layout placeholder only. The companion Portal mounts to the explicit Activity overlay host and never falls back to `document.body`. That host uses the fixed Flower band defined by [Env App floating layer order](env-app-floating-layer-order.md), so an expanded or transitioning companion remains above every movable product or plugin window but below the plugin launcher Panel, blocking product modals, and command palette. A missing or disconnected replacement mount retains the previous shell hidden and inert until the requested mount and anchor are ready.

The desktop environment entry shows its source icon and name without a separate badge or identity frame. Hover or keyboard focus reveals its existing runtime details; a click pins them, and another click, Escape, or outside interaction dismisses them. The environment ID and source type remain in those details. Connection status stays visible; Audit log and Reconnect use compact icon buttons with localized accessible names, full tooltips, and their existing permission and recovery guards. Metrics retain the [runtime read-permission boundary](../architecture/runtime-session-permission-gates.md).

Shell geometry is an EnvApp bootstrap dependency, not a lazy Flower-product detail. Anchor, overlay, Bottom Bar, mobile rail, and product-root geometry styles load with the main EnvApp stylesheet so the anchor has measurable size before `BottomBarCompanion` creates its content host. The Activity registry always registers the full-page Flower host because registry membership is fixed when the runtime owner mounts. Access readiness still gates every Flower entry, command, companion mount request, and navigation action. Conditional visibility must not be implemented by conditionally registering the host or lazily loading the anchor geometry. The Shell imports the lightweight draft coordinator directly; the Flower product surface stays behind its existing lazy entry instead of entering the initial graph through the product barrel.

The companion is absent while password access is checking, locked, or resuming. Recovery, Workbench foreground, the Ask Flower launcher, and the dedicated Flower page hide the retained companion without discarding Flower state. A running task never prevents the user from collapsing the companion or clicking another surface.

## Stable Flower placement

Redeven owns one stable product Portal around exactly one `EnvAIPage`. That owner mounts outside the Activity and Workbench mode views, so starting directly in a persisted Workbench mode does not depend on Activity rendering first. Its requested target is the connected companion content host, dedicated Activity full-page host, or available and unfiltered Workbench Flower host. The Workbench widget contributes only that host; it never constructs an adapter or Flower surface. While that widget remains available and unfiltered in Workbench, its host stays foreground and engaged even when a background pointer gesture clears selection or its canvas lifecycle becomes cold. Permission loss, filtering, or host disposal withdraws the host. Target replacement is atomic: if the requested host is unavailable, the product tree remains in its previous connected host hidden, inert, and disengaged. Neither the shell Portal nor the product Portal uses an implicit body mount.

The ordinary Flower composer textarea is literally the collapsed Bottom Bar field and the expanded detail composer. Expansion and collapse do not clone, replace, crossfade, or copy its value, selection, focus, or composition state. User focus, clicking, or typing in the collapsed textarea requests expansion while that same node remains mounted. Escape focus restoration is explicitly non-activating; a later click reopens even if the editor remains focused. The old quick-entry input, quick draft, IME bridge, composer handoff request, and manual frame resolver do not exist.

Collapsed presentation hides and disengages the header, transcript, thread rail, status lanes, and supporting composer controls. Every pending input request, approval, or Computer takeover uses one compact action, including plain writing, secret questions, and select-or-write questions with a custom answer. Answer mode and progress never change this entry into an editor. Decision controls remain mounted, hidden, and inert while collapsed; existing editors retain their nodes, drafts, and selection. Ordinary questions show the public summary, then the active question, then localized action copy. Secret, approval, and Computer actions use generic localized copy; answer values and another thread's status never become their labels. Read-only or temporarily unavailable editors retain an enabled inspection entry. [Flower companion presence](flower-companion-presence.md) owns the complete entry precedence.

The content button and unused composer space share one activation route and exact target thread. The title exclusively opens the conversation switcher with expansion. Native editor selection and IME behavior remain intact; opening never submits an answer, selects an option, starts work, or stops work. Pointer activation of an entry button places focus in the retained reading surface without focusing a text field. Keyboard question activation focuses the current custom/text editor, selected choice, first available choice, or question region in that order. Approval and Computer entry activation focus their explanation region.

When the collapsed companion has no selected thread, its conversation switcher remains as a compact Flower icon-only button. It omits the fallback `Ask Flower` title, chevron, and title-width reservation so the ordinary composer owns the released space. The icon keeps the localized conversation-switcher accessible name and tooltip; activation opens the companion and its existing thread switcher, including new-conversation entry. Once a thread is selected, the compact title and chevron return. Pending input, approval, and active-work summary precedence remains unchanged.

Expanded companion presentation keeps one stable ordinary chat composer. Its textarea grows from one through five visual lines using measured line height and `scrollHeight`, then keeps the five-line height and scrolls internally from the sixth line. Soft wrapping, IME completion, connection-local updates, width changes, font readiness, clearing, and expansion all schedule the same coalesced measurement. Collapsed presentation suspends measurement and restores the single-line shell geometry. The textarea occupies the flexible track; Attachment and More form an adjacent zero-gap pair of 44 CSS pixel targets before Send. Working directory, permission, model and reasoning, and context usage remain available from the upward-opening More panel instead of creating a second footer row. Setup, model-source recovery, handler failure, detail loading, read-only, approval, and user-input composers retain their complete specialized layout. The dedicated Flower page uses the same one-to-five-line composer behavior.

An empty expanded companion keeps the Flower identity, concise description, and composer guidance, but does not mount starter task suggestions. The bounded detail surface prioritizes transcript and composer space and does not reserve blank placeholders for the omitted controls. The dedicated Flower page retains the complete starter suggestion grid and its prompt-to-composer actions.

Opening animates the width and height of one shell together, growing upward and outward from the compact entry while preserving its bottom edge and continuous border, background, and clipping boundary. The bottom edge is clamped only if the anchor extends beyond the safe visual viewport. Opening and closing use the same reversible 360ms geometry curve. Closing keeps valid geometry through every transition frame, including a rapid reversal. It never clears fixed coordinates during exit, never flashes at the viewport origin, and never changes Activity body height. Reduced motion applies the same final state without geometry or glyph animation.

The published `BottomBarCompanion` owns the collapsed surface's only visible outline, background, radius, and clipping. The retained Flower composer has no border, background, radius, shadow, or backdrop filter while collapsed, including focused, loading, pending-action, and attachment-drag states. Expanded content remains available during the closing geometry transition; the compact presentation returns when the shell reaches its anchor. Expanded and transitioning companion shells use one opaque published popover surface and neutral floating shadow. Their editor retains one input boundary without an additional shadow. The brand icon and collapsed running, waiting, completion, and failure states have no breathing, sweeping light, or halo; state text and local progress symbols remain visible. Non-collapsed editors own their ordinary composer decoration independently. Flower's custom composer uses its own structural styles rather than borrowing the upstream `ChatInput` skin. Visual regression fixtures must include the production `flower-surface` class and verify computed styles; source-rule presence alone cannot prove CSS cascade behavior.

## Contextual Ask Flower

Activity and Workbench keep the existing `FlowerTurnLauncherWindow` interaction. Opening records the exact origin mode, Activity surface, companion placement, and Workbench anchor where applicable. The Activity Flower instance remains the presence owner but is hidden, inert, disengaged, and unable to acknowledge transcript reads while its launcher is open.

Successful submit closes the launcher and focuses the accepted thread. From ordinary Activity it opens the companion detail surface; from the dedicated Flower page it stays full page. Workbench retains its existing widget handoff. Cancel restores the captured origin. Send and context-action behavior remain defined by [Flower turn launcher](flower-turn-launcher.md).

## Presence and summary

[Flower companion presence](flower-companion-presence.md) owns collapsed status priority, live output tails, completion acknowledgement, composer precedence, and the single workspace observation stream. Presence never changes the placement and focus ownership defined here.

## Dismissal, focus, and reads

Capture-phase outside pointer dismissal includes the companion shell, its anchor, and explicitly classified Flower-owned Portal surfaces. Unrelated dialogs, menus, and application surfaces are outside even if they later stop propagation. Activity plugin windows additionally project host pointer and focus input plus trusted iframe bridge activation, focus, and action events into the same outside-dismiss behavior, because cross-origin iframe events cannot bubble into the product document. Programmatic plugin-window ordering remains a pure stack operation and does not impersonate user interaction. Outside dismissal does not prevent the destination interaction or restore focus. The explicit header close control moves focus to the Activity neutral viewport anchor and collapses without issuing a composer-focus request, so closing does not reclaim editing focus. Escape is observed in bubble phase so an owned Portal can consume it first; otherwise it collapses only for companion-owned focus. Once the shell reaches its collapsed phase, Escape returns focus to the visible entry or retained ordinary editor without reopening. The expanded content remains mounted through the entire closing phase, including the interval before the shell reports `collapsing`.

Focus handoffs are consumed once and scoped to the current Flower instance, initiating focus owner, thread, and question/approval identity. Replacement prompts, thread changes, reversed dismissal, external focus transfer, hidden placement, or disposal cancel obsolete handoffs. Background state changes never request focus or expansion. Focus queries never recover through another Flower instance.

Every Activity `markThreadRead` call requires Activity foreground, document visibility, a visible and engaged expanded/full-page placement, no launcher, the current chat panel, exact selected detail, a matching after-paint content-presented token, and no bootstrap, loading, or error state. Collapsed presentation, including its unread failure summary and read-only summary stream, staging between Portal hosts, Workbench foreground, launcher presentation, and access gates cannot acknowledge reads. This keeps a failure visible until the user opens its exact thread and genuinely sees it. Read acknowledgement has one durable watermark: `activity_revision`. One selection cycle attempts each revision at most once, coalesces in-flight updates to the greatest pending revision, and restores unread presentation after failure without polling or automatic retry. A newer revision or a later genuine presentation cycle may submit again. Canonical SSE summary batches never contain private read state; viewer read-state envelopes are scoped to the same `UserPublicID` and never enter shared summary or timeline history.

# Boundaries

The Workbench Flower widget retains its existing window, canvas, and focus contracts while contributing only a placement host for the Env App-owned Flower product. Selection, z-order, and canvas lifecycle do not own product residency. Host movement adds no persistent transcript cache, lifecycle endpoint, alternate command path, or second live reducer. Related Flower dialogs and previews may continue using their established floating primitives; only the Bottom Bar companion shell is forbidden from doing so.

The companion never auto-expands for completion, failure, approval, or user input. Presence communicates progress without stealing focus; explicit activation selects the associated thread before expansion. Selecting Flower from the Activity Bar enters the dedicated page; the Bottom Bar and ordinary Activity Ask Flower handoff enter the bounded companion detail surface. Showing an available, unfiltered Workbench Flower widget moves the retained product tree into that widget without starting a second list load or live stream, and later canvas deselection does not move it away.
