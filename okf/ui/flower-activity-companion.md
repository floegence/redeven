# Summary

After access first becomes ready, Env App owns one stable `EnvAIPage` and `FlowerSurface`. The published `BottomBarCompanion` provides a centered collapsed field and a bounded detail surface that grows upward without changing body geometry. The dedicated Activity Bar page and an available, unfiltered Workbench Flower widget are placements of that same product tree. Workbench selection controls canvas input and focus only; clearing selection never revokes Flower placement or engagement. Placement changes hosts, presentation, visibility, and engagement; it never creates a second Flower surface or changes Floret authority. Floret owns thread lifecycle state, while Redeven owns product placement, read acknowledgement, and ephemeral UI state.

# Contract

## Companion ownership

`@floegence/floe-webapp-core/layout` owns the reusable companion shell, fixed geometry, visual-viewport and safe-area clamping, motion phases, capture-phase outside dismissal, Escape routing, and explicit mount handling. Redeven consumes the published package and does not reuse `FloatingWindow` or `SurfaceFloatingLayer` for this surface. The companion has independent `retained`, `visible`, and `open` inputs: residency, product availability, and expanded geometry are not aliases for one another.

The desktop Bottom Bar keeps a symmetric three-track layout so the anchor stays centered independently of environment and status controls. Mobile uses one product-owned fixed anchor rail above the measured mobile tab bar. Each anchor is a layout placeholder only. The companion Portal mounts to the explicit Activity overlay host and never falls back to `document.body`. That host uses the fixed Flower band defined by [Env App floating layer order](env-app-floating-layer-order.md), so an expanded or transitioning companion remains above every movable product or plugin window but below the plugin launcher Panel, blocking product modals, and command palette. A missing or disconnected replacement mount retains the previous shell hidden and inert until the requested mount and anchor are ready.

Shell geometry is an EnvApp bootstrap dependency, not a lazy Flower-product detail. Anchor, overlay, Bottom Bar, mobile rail, and product-root geometry styles load with the main EnvApp stylesheet so the anchor has measurable size before `BottomBarCompanion` creates its content host. The Activity registry always registers the full-page Flower host because registry membership is fixed when the runtime owner mounts. Access readiness still gates every Flower entry, command, companion mount request, and navigation action. Conditional visibility must not be implemented by conditionally registering the host or lazily loading the anchor geometry.

The companion is absent while password access is checking, locked, or resuming. Recovery, Workbench foreground, the Ask Flower launcher, and the dedicated Flower page hide the retained companion without discarding Flower state. A running task never prevents the user from collapsing the companion or clicking another surface.

## Stable Flower placement

Redeven owns one stable product Portal around exactly one `EnvAIPage`. That owner mounts outside the Activity and Workbench mode views, so starting directly in a persisted Workbench mode does not depend on Activity rendering first. Its requested target is the connected companion content host, dedicated Activity full-page host, or available and unfiltered Workbench Flower host. The Workbench widget contributes only that host; it never constructs an adapter or Flower surface. While that widget remains available and unfiltered in Workbench, its host stays foreground and engaged even when a background pointer gesture clears selection or its canvas lifecycle becomes cold. Permission loss, filtering, or host disposal withdraws the host. Target replacement is atomic: if the requested host is unavailable, the product tree remains in its previous connected host hidden, inert, and disengaged. Neither the shell Portal nor the product Portal uses an implicit body mount.

The ordinary Flower composer textarea is literally the collapsed Bottom Bar field and the expanded detail composer. Expansion and collapse do not clone, replace, crossfade, or copy its value, selection, focus, or composition state. Focusing or typing in the collapsed textarea requests expansion while that same node remains mounted. The old quick-entry input, quick draft, IME bridge, composer handoff request, and manual frame resolver do not exist.

Collapsed presentation hides and disengages the header, transcript, thread rail, status lanes, and supporting composer controls while retaining the ordinary textarea. Canonical secret questions and approval decisions are different composer kinds: collapsed presentation shows a compact action that opens the detail surface, while the real password or approval control remains hidden and inert. A presentation change itself never changes composer kind.

When the collapsed companion has no selected thread, its conversation switcher remains as a compact Flower icon-only button. It omits the fallback `Ask Flower` title, chevron, and title-width reservation so the ordinary composer owns the released space. The icon keeps the localized conversation-switcher accessible name and tooltip; activation opens the companion and its existing thread switcher, including new-conversation entry. Once a thread is selected, the compact title and chevron return. Pending input, approval, and active-work summary precedence remains unchanged.

Expanded companion presentation keeps one stable ordinary chat composer. Its textarea grows from one through five visual lines using measured line height and `scrollHeight`, then keeps the five-line height and scrolls internally from the sixth line. Soft wrapping, IME completion, connection-local updates, width changes, font readiness, clearing, and expansion all schedule the same coalesced measurement. Collapsed presentation suspends measurement and restores the single-line shell geometry. The textarea occupies the flexible track; Attachment and More form an adjacent zero-gap pair of 44 CSS pixel targets before Send. Working directory, permission, model and reasoning, and context usage remain available from the upward-opening More panel instead of creating a second footer row. Setup, model-source recovery, handler failure, detail loading, read-only, approval, and user-input composers retain their complete specialized layout. The dedicated Flower page uses the same one-to-five-line composer behavior.

An empty expanded companion keeps the Flower identity, concise description, and composer guidance, but does not mount starter task suggestions. The bounded detail surface prioritizes transcript and composer space and does not reserve blank placeholders for the omitted controls. The dedicated Flower page retains the complete starter suggestion grid and its prompt-to-composer actions.

Opening animates one shell upward from the anchor while preserving its bottom edge, width, border, background, and clipping boundary. Closing keeps valid geometry through every transition frame. It never clears fixed coordinates during exit, never flashes at the viewport origin, and never changes Activity body height. Reduced motion applies the same final state without geometry or glyph animation.

## Contextual Ask Flower

Activity and Workbench keep the existing `FlowerTurnLauncherWindow` interaction. Opening records the exact origin mode, Activity surface, companion placement, and Workbench anchor where applicable. The Activity Flower instance remains the presence owner but is hidden, inert, disengaged, and unable to acknowledge transcript reads while its launcher is open.

Successful submit closes the launcher and focuses the accepted thread. From ordinary Activity it opens the companion detail surface; from the dedicated Flower page it stays full page. Workbench retains its existing widget handoff. Cancel restores the captured origin. Send and context-action behavior remain defined by [Flower turn launcher](flower-turn-launcher.md).

## Presence and summary

Bottom Bar presence is a pure canonical summary projection with active work first: running, queued, attention, unread failure, unread canceled, unread completed, unavailable, idle. A selected pending approval or secret-input action has higher visual priority than that projection because it is an actionable composer kind, not a historical presence count. The per-thread classifier uses the same active-first order, so a running or queued turn is not swallowed by an older waiting or terminal status on that thread. Counts for every canonical group remain available to the expanded Flower UI; running, queued, and canonical unread failure qualify for collapsed Bottom Bar presentation. A displayed title consumes the non-empty canonical title in ready, pending, or failed automatic-title state because Floret retains the first-message fallback until provider success. Empty or missing titles and inferred preview text are not usable. Companion presence still covers the complete summary collection, including titleless threads filtered out of the sidebar list, and every displayable status carries its exact target thread identity.

The collapsed visual line describes current work instead of exposing aggregate counters. Running shows its live progress, queued shows an explicit waiting-to-start summary, and an unread failed thread shows a localized task failure until the exact thread has genuinely been displayed and canonical read state clears it. While current detail remains cached, a documented safe error code may contribute its localized reason; unknown or reload-only failure detail falls back to the canonical title or generic localized Flower failure copy and never exposes an arbitrary provider message. Attention without a selected actionable composer, cancellation, and historical completion do not produce a collapsed summary, colored marker, tooltip, accessible name, or live announcement. Bare aggregate output such as `Failed · 1`, `Needs review`, or `One task needs your attention` remains forbidden. The expanded companion and dedicated Flower page remain the complete surfaces for inspecting and acting on all thread states.

Running work is a live tail of the priority thread's current active run, never its user input, an earlier run, or inferred thread-title text. Before visible output arrives, canonical `preparing`, `waiting_response`, `retrying`, `streaming`, and `finalizing` phases produce the localized status, including `Waiting for model response...` and `Thinking...`. Raw thinking content is not exposed. Once the latest active-run block is visible, a tool timeline block contributes its existing compact activity presentation and an assistant text or Markdown block contributes its whitespace-collapsed latest output. Block order decides which one is current.

The running visual line contains only that status, tool summary, or output; the thread title and aggregate count do not compete for its single row. Assistant output uses a clipped normal-flow viewport. Only overflow enables the leading fade and ellipsis. Stable thread, active turn, message, and block identity plus reliable rolling-window overlap reconstruct genuine appends locally, and one animation-frame follower advances smoothly toward the newest edge as tokens arrive. Identity changes, rewrites, current-view replacement, expansion, hidden state, reduced motion, or a large burst snap directly to the newest text. The reconstruction buffer has a hard bound and compensates scroll when trimming content already offscreen. Tool summaries preserve their action-leading text and use ordinary end ellipsis, as do status and queued summaries. The button tooltip and accessible name expose the complete current text and add any remaining running count. Phase, completion, and failure changes use a restrained polite atomic announcement, while high-frequency tool and output changes do not trigger repeated live announcements. Running uses a low-intensity glyph breath, a low-frequency status pulse, and a one-pixel flowing highlight instead of visible rotation. Completion settles once into a green wash, while failure flashes a red edge once and then stays static. Reduced motion disables breathing, flow, transition tracking, and arrival motion while retaining semantic color, icon, and text.

A successful transition for a run that the collapsed companion previously observed as running may temporarily replace the idle composer with one localized completion acknowledgement. This is ephemeral product feedback, not canonical completed presence: initial history, queued-only work, failures, cancellations, attention, mismatched or expired turns, and completion while any running or queued work remains never trigger it. A process-local observer binds only accepted `thread.batch current` active turns to a local generation and emits a receipt only for that same turn's later accepted terminal view. The identity-bound completion controller tolerates the short gap between live terminal state and canonical summary, shows the acknowledgement for about four seconds without refresh extending it, and prevents an older timer from clearing a newer acknowledgement. New work, access loss, opening the companion, entering the dedicated Flower page, or disposal clears it immediately. The completion state uses a success point, soft wash, and one restrained settle motion; reduced motion keeps the same static semantic state. It sends one polite atomic announcement and selects its exact thread before opening Flower detail. Historical completion remains forbidden from the collapsed Bottom Bar.

The companion consumes the same single workspace SSE as the full Flower surface. Complete summary batches remain the authority for lifecycle counts and unread state. Matching cached typed current detail contributes only the active run's visible output, tool presentation, and documented safe localized failure reason; it never mutates or replaces the summary projection. Accepted typed current updates also feed the process-local terminal observer without adding a selection-specific connection. `LiveTransport` fences stale callbacks with its process-local connection epoch and reconnects with bounded backoff. After disconnect it refreshes summaries and the selected current view; it does not poll, replay cursors, or run a second companion transport.

The visible presence owner performs one initial summary bootstrap and then relies on SSE `summary.batch` envelopes. There is no 1.8-second inventory timer, fixed live-event polling loop, or background full-history refresh. Heartbeats keep a healthy connection alive without application requests; inactivity aborts the reader after 45 seconds and lets the bounded reconnect policy recover. Hidden or disposed documents clear the reader and renderer work, so idle observation does not create a CPU or network loop. Expansion keeps the same connection and requests the selected thread current view rather than creating a second stream.

The collapsed companion has three mutually exclusive content classes, in priority order: a pending approval or secret-input action; a running, queued, unread-failure, or eligible ephemeral-completion status button; or the ordinary textarea. A status button contains the Flower glyph, semantic marker, and single-line summary, selects its exact target thread, and only then opens the companion detail surface. It appears only when the textarea draft is empty after trimming, focus is elsewhere, and IME composition is inactive. A pending action owns both visible and accessible status through its explicit action button; the companion summary live region is absent while that button is shown. While a status or pending action is visible, the ordinary textarea remains mounted for identity continuity but its content container is hidden, `inert`, and removed from accessibility navigation. There is no draft recovery, conflict, takeover, or store-unavailable presentation. A connection-local draft, caret, selection, or composition session otherwise always wins.

## Dismissal, focus, and reads

Capture-phase outside pointer dismissal includes the companion shell, its anchor, and explicitly classified Flower-owned Portal surfaces. Unrelated dialogs, menus, and application surfaces are outside even if they later stop propagation. Activity plugin windows additionally project host pointer and focus input plus trusted iframe bridge activation, focus, and action events into the same outside-dismiss behavior, because cross-origin iframe events cannot bubble into the product document. Programmatic plugin-window ordering remains a pure stack operation and does not impersonate user interaction. Outside dismissal does not prevent the destination interaction or restore focus. The explicit header close control moves focus to the Activity neutral viewport anchor and collapses without issuing a composer-focus request, because focusing the collapsed composer is itself an expand intent. Escape is observed in bubble phase so an owned Portal can consume it first; otherwise it collapses only for companion-owned focus and returns focus to the retained composer or compact action.

Every Activity `markThreadRead` call requires Activity foreground, document visibility, a visible and engaged expanded/full-page placement, no launcher, the current chat panel, exact selected detail, a matching after-paint content-presented token, and no bootstrap, loading, or error state. Collapsed presentation, including its unread failure summary and read-only summary stream, staging between Portal hosts, Workbench foreground, launcher presentation, and access gates cannot acknowledge reads. This keeps a failure visible until the user opens its exact thread and genuinely sees it. Canonical SSE summary batches never contain private read state; viewer read-state envelopes are scoped to the same `UserPublicID` and never enter shared summary or timeline history.

# Boundaries

The Workbench Flower widget retains its existing window, canvas, and focus contracts while contributing only a placement host for the Env App-owned Flower product. Selection, z-order, and canvas lifecycle do not own product residency. Host movement adds no persistent transcript cache, lifecycle endpoint, alternate command path, or second live reducer. Related Flower dialogs and previews may continue using their established floating primitives; only the Bottom Bar companion shell is forbidden from doing so.

The companion never auto-expands for completion, failure, approval, or user input. Presence communicates progress without stealing focus; explicit activation selects the associated thread before expansion. Selecting Flower from the Activity Bar enters the dedicated page; the Bottom Bar and ordinary Activity Ask Flower handoff enter the bounded companion detail surface. Showing an available, unfiltered Workbench Flower widget moves the retained product tree into that widget without starting a second list load or live stream, and later canvas deselection does not move it away.
